# 作品个人评分改为百分制（2026-10-28）

当前源码的作品 `rating` 为 0–100，100 满分，85 等同原 8.5。空值表示未评分，0 是有效评分。后台默认按整数步进；标准 API 保留有必要的小数精度，输入 8.5 就是百分制的 8.5，不按大小猜测旧量表。Bangumi 社区评分保留来源量表；旧 Bangumi 收藏页的本人评分仅在展示时从来源十分制换算为百分制。

Payload 的 `works.rating` 与 `_works_v.version_rating` 继续使用原 numeric 列，无需表重建。注册迁移 `20261028_120000_rating_scale_100` 是数据迁移，其 JSON 与前一个 schema 快照一致。迁移在一个事务内检查所有旧值为 0–10，再逐行十倍换算两表各自的数值；空值、0、主表与草稿／发布／旧版本之间的差异全部保留。转换不调用发布 API、不生成版本、不修改更新时间、公开状态、ID、数组、关系、正文或其他字段。按原数字的十进制表示移动小数位，避免浮点尾数且不统一取整。

事务内同时写 `payload_migrations.name=data:personal-rating-scale:100:v1`（batch 0）作为数据量表标记；Payload 随后记录正式迁移名。两步之间中断时，重跑仅补正式记录，不再乘十。没有标记但遇到越界旧数据时整个迁移拒绝执行，不能根据 <=10 猜测单条数据是否已转换。`down` 始终拒绝反向改写，回退应用必须兼容百分制。

部署需与 Markdown 库端在一个维护窗口协调：先安装审查过的新版 deployer，再暂停写入、Markdown 网站同步与内容 publisher，记录现状并一致备份；使用固定新镜像在备份副本演练后，对正式库运行现有迁移入口（`PAYLOAD_IMPORT_TRANSACTION=0`），切换 API、源码及静态构建，再核对后恢复定时器。自动部署不会执行迁移。不能先把新网站校验接到旧数据，也不能迁移后启动旧十分制代码。deployer 以正式迁移记录或原子量表标记阻止旧版回退，包含空库／全低分；正常部署要求两个记录完整，并只排除这个已知的 batch 0 标记后精确比较迁移历史。失败时保留原静态站与兼容应用／数据，不覆盖维护期间的编辑。

新 JSON／API 清单默认百分制。旧作品 Markdown 清单须显式指定 `scripts/import-works-log.ts ... --rating-scale=10`；默认 `--rating-scale=100`。两种输入都会校验各自范围，再输出百分制。SQLite legacy 导入不能只凭 schema 一致自动标记这项数据迁移已运行；原始十分制副本保留未执行状态，百分制副本必须同时保留两个量表记录，缺一项时先完成源端迁移再导入。

验证：临时 SQLite 覆盖 6 条作品及独立版本；中途异常全事务回滚、混合量表拒绝、提交后迁移记账前中断重跑、双重重跑、所有非评分列与表不变、公开 85／草稿 83.7 同时保留、原生 REST 草稿写入 0／85／100／83.75／8.5／空值与越界拒绝、schema 零差异、完整性与外键通过。`deploy/server/test-deploy-release.py` 包含 marker 与 ledger 单独阻止旧版、完整记账要求，以及升级构建失败保留兼容应用和旧静态站。

本说明是源码与临时数据库验证记录，生产迁移／部署以执行方现场证据为准。
